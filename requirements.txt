# onnxruntime 1.28's CUDA provider wants CUDA 13 and cuDNN 9. torch ships its
# own CUDA 12.8 libraries in torch/lib, which are the wrong major version, so
# these supply CUDA 13 alongside them. ~850 MB.
#
# The two sets coexist only *carefully*. cublas64_12 and cublas64_13 differ by
# name and are fine. cuDNN does not: both builds are called cudnn64_9.dll, and
# Windows keeps one DLL per name per process. If onnxruntime loads its copy
# first, torch then fails at import with
#
#     OSError: [WinError 127] ... torch\lib\cudnn_cnn64_9.dll
#
# which names torch's file and never mentions the TTS. This broke every turn of
# the voice loop once. src/tts/kokoro.py handles it: torch is imported before
# the CUDA session is built, and these directories go on PATH only while it is
# being built. tests/test_hardware.py guards both halves.
#
# Note the naming: for CUDA 13 the `-cu13` suffix was dropped from some of
# these. `nvidia-cublas-cu13` and `nvidia-cuda-runtime-cu13` exist on PyPI as
# empty 1.4 kB placeholders that fail to build; the real wheels are these.
#
# src/tts/kokoro.py has to put them on PATH at load: onnxruntime loads its
# provider DLL from native code, and Windows resolves that DLL's dependencies
# by the ordinary search order.
nvidia-cudnn-cu13>=9.24
nvidia-cublas>=13.6
nvidia-cuda-runtime>=13.3
